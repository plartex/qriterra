# Проектная оценка и семантика межфайлового анализа

[English](../project-evaluation.md) | [Русский](project-evaluation.md)

Режим проектной проверки (`EvaluationTarget.project`) предназначен для комплексного аудита всей кодовой базы или репозитория. Вместо простой передачи текста в промпт или статического анализа синтаксических деревьев Qriterra предоставляет агенту интерактивные инструменты поиска и чтения файлов в рамках единой сессии для выявления сложных межмодульных запахов кода.

---

## 1. Отличия проектного анализа от сниппетов и одиночных файлов

| Аспект | `snippet` / `file` | `project` |
|---|---|---|
| **Передача контекста** | Встраивается в текст запроса (< 1 МБ) | Передаётся путь к каталогу; агент исследует файлы инструментами |
| **Инструменты агента** | `tool_policy="no_tools"` (закрытый режим) | Разрешены инструменты чтения и поиска (`read_only` или `full_access`) |
| **Схема ответа** | Схема 1.0 (плоский список `evidence`) | Схема 2.0 (группированные находки `findings`, декларируемый `coverage`) |
| **Управление сессией** | Опционально (`--no-session` разрешён) | Требуется строго **одна** непрерывная сессия для всех пакетов |
| **Требование к охвату**| По умолчанию полный для переданного кода | Декларируемый статус `complete` или `partial` для каждого правила |

## 2. Исследование агентом и семантические суждения

Традиционные линтеры и детекторы дублирования (такие как CPD или AST-диффы) ориентируются на лексическую или синтаксическую идентичность токенов. В отличие от них, Qriterra выполняет **семантическое исследование силами LLM**:

1. **Инструментальное исследование**: Агент получает корневой каталог и определения правил. С помощью инструментов чтения и поиска (поиск по шаблонам, просмотр структуры, чтение файлов) он исследует границы модулей, иерархии наследования и потоки данных.
2. **Семантическое понимание**: Модель способна обнаружить проблемы, недоступные синтаксическим парсерам:
   - **Семантическое дублирование**: две функции с абсолютно разными именами переменных и разной структурой циклов, решающие одну и ту же прикладную задачу с идентичной бизнес-логикой и обработкой краевых случаев.
   - **Циклические зависимости и утечки слоёв**: бизнес-сущности ядра, напрямую импортирующие низкоуровневые адаптеры базы данных или пользовательского интерфейса.
   - **Раздутые интерфейсы и сквозные изменения (Shotgun Surgery)**: изменение одной бизнес-концепции, требующее правок в десятках разрозненных файлов.
3. **Метрики как ориентиры**: Пороговые значения в каталоге (например, `token_similarity > 85%` или `cyclomatic_complexity > 10`) служат для модели ориентиром, а не автоматическим скриптом. Решение принимает агент на основе инженерного анализа.

## 3. Схема 2.0: Группировка находок и верификация цитат

При проверке отдельного файла (Схема 1.0) каждое нарушение указывает на конкретное место в одном файле. В проекте нарушение часто распределено между несколькими файлами. Для этого разработана Схема 2.0:

```json
{
  "schema_version": "2.0",
  "batch_id": "batch-0001",
  "results": [
    {
      "rule_id": "duplicate_code",
      "status": "failed",
      "confidence": 0.95,
      "findings": [
        {
          "summary": "Логика расчёта региональных налогов продублирована в биллинге и корзине",
          "evidence": [
            {
              "path": "src/billing/invoice.py",
              "start_line": 42,
              "end_line": 56,
              "excerpt": "def calculate_state_tax(amount, state):\n    rates = {'NY': 0.08875, 'CA': 0.0725}\n    return amount * rates.get(state, 0.0)",
              "reason": "Основная таблица ставок и множитель налога"
            },
            {
              "path": "src/cart/checkout.py",
              "start_line": 105,
              "end_line": 119,
              "excerpt": "def compute_taxes(subtotal, region):\n    lookup = {'NY': 0.08875, 'CA': 0.0725}\n    return subtotal * lookup.get(region, 0.0)",
              "reason": "Повторная реализация той же региональной таблицы с переименованными переменными"
            }
          ]
        }
      ],
      "coverage": {
        "status": "complete",
        "inspected_paths": [
          "src/billing/invoice.py",
          "src/cart/checkout.py",
          "src/common/pricing.py"
        ],
        "limitations": []
      }
    }
  ]
}
```

### Строгая верификация цитат по файлам

Чтобы исключить галлюцинации языковой модели, валидатор ответов Qriterra проверяет каждую цитату:
- Путь `path` должен указывать на реально существующий файл внутри целевого каталога (символические ссылки, ведущие наружу, отклоняются).
- Диапазон строк `start_line` и `end_line` не должен выходить за фактическое число строк в файле.
- **Цитата `excerpt` физически сопоставляется** с содержимым файла на диске в диапазоне строк `[start_line, end_line]`. Если модель цитирует код, отсутствующий в файле, ответ бракуется и отправляется на повторное исправление (repair).

## 4. Семантика охвата: Complete против Partial

Ключевой архитектурный принцип чекера: **декларируемый агентом охват является самоотчётом, а не математическим доказательством исчерпывающего анализа**. В связи с этим действуют строгие правила:

### Полный охват (Complete Coverage)
- `status: "complete"`
- Обязан содержать непустой массив `inspected_paths`.
- Массив `limitations` обязан быть пустым.
- Статус **`passed`** разрешён **только** при охвате `complete`.

### Неполный охват (Partial Coverage)
- `status: "partial"`
- Массив `limitations` обязан содержать явное перечисление причин (например: исчерпан лимит времени, не исследованы динамические вызовы, пропущены подкаталоги).
- **Правило с неполным охватом НЕ МОЖЕТ получить статус `passed`**: если агент возвращает `passed` при `coverage.status: "partial"`, валидатор фиксирует протокольную ошибку.
- Если агент проверил проект частично и запаха не обнаружил, он обязан вернуть статус **`inconclusive`** с описанием причины.
- Статус **`failed`** разрешён при `partial`, если найдено и подтверждено реальное нарушение до завершения полного обхода проекта.

## 5. Требования к сессии и бюджет времени

1. **Единая сессия (`use_session=True`)**:
   - CLI и MCP открывают одну сессию Agent Shuttle на весь запуск.
   - Все пакеты правил выполняются в контексте одного диалога, что позволяет модели сохранять ментальную карту проекта.
   - Флаг `--no-session` для проектных целей запрещён и вызывает ошибку `ValueError`.
2. **Сверка рабочей области (Workspace)**:
   - До вызова модели чекер запрашивает идентичность сервера Agent Shuttle. Если рабочая папка сервера не совпадает с каноническим путём к целевому проекту, запуск отклоняется.
3. **Бюджет времени (`--max-project-seconds`)**:
   - По умолчанию: `1800` секунд (30 минут).
   - Если общее время выполнения превышает лимит в процессе обработки пакета, текущий и оставшиеся пакеты прерываются.
   - Оставшиеся правила получают статус **`inconclusive`** с формулировкой `"Project time budget of ...s exhausted"` и неполным охватом.
   - При наличии неполного охвата итоговая оценка качества `quality_score` становится равной `null` (`N/A`).

## 6. Затраты токенов и замеры live-прогонов

Полное сканирование проектов требует глубокого контекста и активно расходует квоту модели.

> [!WARNING]
> **Пример реального замера (Benchmark)**:
> В контрольном запуске на Google Antigravity при анализе всего **двух файлов** и **одного правила** (`duplicate_code`):
> - **Время выполнения**: 173.5 секунды (~2.9 минуты).
> - **Расход токенов**: 205 154 токена суммарно.
>
> Полное сканирование всех 80 правил на большом репозитории займёт значительно больше времени и потребует миллионов токенов.

### Рекомендации по оптимизации проектных проверок:
1. **Фокусируйтесь на целевых правилах**: используйте `--rules` для проверки только архитектурных или межмодульных запахов:
   ```powershell
   qriterra evaluate project path/to/project `
     --rules duplicate_code,cyclic_dependency,shotgun_surgery `
     --max-project-seconds 600
   ```
2. **Контролируйте ход через трассировку**: флаг `--debug` позволяет наблюдать в реальном времени расход токенов и вызовы инструментов.
3. **Начинайте с подкаталогов**: запускайте проверку на отдельных подсистемах перед сканированием всего монорепозитория.
